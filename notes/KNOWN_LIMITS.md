# Known limits

Things fast-ticket does not do yet, or does only partly, that someone relying on it should know.
This is a **live list, not a changelog**: when a limit is fixed its entry is *deleted* (git history keeps
it) and the commit that fixes it says so. Rules for keeping it honest are in `AGENTS.md` → "Known limits".

Last reviewed: 2026-10-05 (not a full review: this session removed the referral entry, narrowed the thread-entry, any-role, forms, custom-answer and compatibility entries it touched, and added the timestamp-timezone, directory and teams/forms entries; the rest were last checked on 2026-10-04 and not re-run). Verified at the end: `make test-e2e` 66 passed.

Each entry: what is true today · what it means for you · what will resolve it (a phase from the plan, or
"by design" if it is a deliberate trade-off).

## Authorization (security overhaul S2–S5)

| Limit | Impact | Resolved by |
|---|---|---|
| **Teams (the list and detail), SLA plans, the form *list and detail* (`/forms`), and the *detail* of departments, topics and priorities are admin-only.** Open to every agent, scoped as osTicket scopes them: the fields of the ticket, user, organization and task forms as osTicket's create/edit pages show them (`GET /forms/for/{kind}`: enabled and agent-visible fields, a ticket's help-topic forms with the fields the topic switches off removed; the rule is the field flags, checked by an e2e test but not by the oracle), the lists for a ticket form (departments, help topics, priorities), the canned-response picker, the agent directory (`GET /agents`) and the assign-form choices for a ticket or task (`GET /tickets/{id}/assignees`, `GET /tasks/{id}/assignees`). | A non-admin agent cannot browse teams, SLAs or forms outside those choices. The assign choices exist only for an *existing* ticket or task: osTicket's other assign forms (mass assign from the ticket list, "assign on create") list agents without an object, and that variant is not exposed. | Next reference-data pass, as needed |
| **The agent directory's text search treats only all-digit terms as phone numbers** (PHP's `is_numeric` also accepts "1.5" and "-3"); assignable-agent names follow the instance's `agent_name_format`, but agents have no salutation or middle name here, so `formal`/`legal`/`complete` render as osTicket would with those parts empty. | A search for "1.5" looks in names and emails, not phones. | By design (not worth porting) |
| **Organization reads require `user.dir`**, which is stricter than osTicket (it does not gate organization pages by URL). | An agent without the user-directory permission cannot list organizations here though osTicket's page would open for them. | By design (nearest real gate) |
| **Role permissions are checked as "any of the agent's roles"** (`hasPerm($perm, false)`) by the API *and* by the bridge's registry check; the exact per-department answer (`getRole($dept)`) is applied only by the ticket and task handlers. | An agent whose role in *another* department grants `canned.manage` can manage canned responses of any department; ticket create is exact (`Ticket::open` checks the create permission in the chosen department's role). Ticket and task commands are exact. | Later (per-department checks in the canned handlers) |
| **A command's secrets stay in the inbox until it finishes.** A `staff.create` password is in the payload while the command is pending or held by a run that was killed; the bridge overwrites it once the command is done or failed, and the API masks it whenever it shows a payload. | Anyone with database access can read a password during that window. | Encrypting sensitive payload fields at rest (with the HMAC work below) |
| **The bridge's permission check is proven live by hand, not by an automated test.** Forged inbox rows from an agent with no permissions were all refused (admin, `user.create`, `ticket.create`, `faq.manage`, `canned.manage`), and a static test checks every command's permission against the API's route guard, but no automated test can insert an inbox row. | A regression in the PHP check would show only in that manual run. | A PHP test runner, or a test-only endpoint |
| **The inbox is unsigned.** A row carries `requested_by_staff_id` and nothing proves the API wrote it. | Anyone with write access to the inbox table can run commands as any agent, including an admin. | Later (optional HMAC) |

## Ticket editing

| Limit | Impact | Resolved by |
|---|---|---|
| **`PATCH /tickets/{id}` takes the due date as UTC** (osTicket's own edit page uses the agent's timezone setting). | A due date entered for another timezone must be converted by the client. | Reading the agent's timezone |
| **Release needs the `ticket.release` role permission through the API; osTicket also lets a department manager release without it** (`ajax.tickets.php`: `PERM_RELEASE \|\| isManager()`). The bridge handler applies osTicket's exact rule, but the registry check in front of it is stricter. | A manager whose role lacks `ticket.release` is refused. Never looser than osTicket. | Registry support for an "or manager" permission |
| **Changing or removing a collaborator needs `ticket.edit`, as adding one does (osTicket's ticket page gates adding on it; its thread pop-ups check only that the agent can open the ticket).** Changing a collaborator's own details (name, email) is not exposed here — use the users API. | Update/remove are stricter than osTicket's pop-ups, so never looser. | By design (nearest real gate) |
| **Thread-entry edit and resend (tickets and tasks) are gated at the API by `ticket.reply` / `task.reply`; the bridge applies osTicket's exact rule** (own post, department manager, or `thread.edit`). "Post a client message" (`Ticket::postMessage`) is not exposed. | An agent without `ticket.reply` who osTicket would let edit (a manager) is refused; an entry's edit history is not readable (only the current version is listed, with `is_edited`). | Message posting only if needed |
| **Form fields of a custom-list type (`list-<id>`) can be added, but custom lists themselves cannot be created or edited through the API.** Field configuration covers the common types (text, memo, bool, choices, datetime, phone, info); `min`/`max` of date fields and the file-upload options are not exposed. | Build the list in osTicket's Admin Panel first. | Wave 2 (custom lists) |
| **Adding or removing a field on a core form (ticket, task, user, organization) makes osTicket rebuild that form's `__cdata` table** (its own behaviour, via a signal). | A busy helpdesk may stall briefly on a large ticket table. Ticket reads were verified to survive the rebuild. | By design (osTicket) |
| **Custom-field answers are read typed and written as osTicket's parsers accept them.** A read returns `kind` (`text` \| `bool` \| `choices`) with `bool_value` or `choices` (`[{key,label}]`) beside osTicket's stored `value` / `value_id`; a multiple choice stored as a plain key list gets its labels from the field's configuration, and a value that does not parse stays text. Writes take a choice key (or a list of keys), a boolean, a number or text. Answers to file-upload and custom-list (`list-N`) fields cannot be written, and a **ticket create** with an invalid choice key is stored as given (osTicket's create does not check it; an update does). When two forms on one ticket define the same variable name, the first wins. | Datetime and number answers are returned as the stored text. A custom-list answer is readable (`kind=choices`, key = item id) but not writable. | Writing custom-list answers; typed datetime values |
| **A required custom field with no answer blocks every `PATCH /tickets/{id}`** (osTicket validates the whole form on each edit, as its own edit page does). | After adding a required field to a ticket form, old tickets must be given an answer on their next edit. | By design (osTicket) |

## Lists and queues

| Limit | Impact | Resolved by |
|---|---|---|
| **Ticket queues are osTicket's eight default ones, fixed in code** (`GET /tickets/queues`, `?queue=`): Open (unanswered, answered, overdue), My Tickets (assigned to me, to my teams), Closed. osTicket keeps its queues in `ost_queue` as an editable query builder; that table is not read. | Custom queues, renamed queues, the "Closed today / this week…" sub-queues and per-queue column or sort settings are not reflected. The default queues' ticket sets are checked against osTicket's own by the oracle test. | By design (the queue query builder is not exposed); read `ost_queue` titles if renames matter |
| **List search (`q`) matches ticket number, subject and the requester's name or email; it does not search message bodies**, and tasks match number and title only. Matching is a plain contains, not osTicket's full-text index. | A word that appears only in a message is not found by the list search. | A full-text search over thread bodies, if a screen needs it |
| **The user directory's `ticket_count` counts all of a user's tickets**, as osTicket's User Directory does, not only those the agent may open; user and organization search are plain "contains" (the user search covers name, any email, organization name and the phone answer, as `users.inc.php`). The knowledge-base search is a plain "contains" over question, answer, keywords and the category's name and description (osTicket's `kb.php`); it has no help-topic filter. | A count can include tickets the agent cannot open (a number only, no data). | By design (osTicket's own behaviour) |
| **Ticket and task sorting covers number, dates, subject/title, status and department; tickets also sort by priority (urgency), assignee and requester.** Tasks have no priority, and sort by assignee or requester is not offered for them. | A task list cannot be ordered by assignee. | As needed |

## Attachments

| Limit | Impact | Resolved by |
|---|---|---|
| **Uploads are size-capped base64 on replies and notes only.** `POST /tickets/{id}/reply`, `POST /tickets/{id}/note`, `POST /tasks/{id}/reply` and `POST /tasks/{id}/note` take `attachments: [{name, content_type?, data}]` (base64; at most `ATTACHMENT_MAX_FILES` files, `ATTACHMENT_MAX_FILE_BYTES` each, `ATTACHMENT_MAX_TOTAL_BYTES` together; osTicket's own `max_file_size` also applies, with its refusal; `GET /settings/attachments` reports the limits). The bytes ride in the command payload and are overwritten once the command finishes. Not yet: files on ticket/task *create*, on canned responses or FAQs, and on custom-form file fields; no streaming upload, so a file is bounded by memory and by the inbox row. Files already on a thread are listed on their entry (`attachments`) and downloaded with `GET /tickets/{id}/attachments/{attachment_id}` (tasks the same), scoped like the thread (404 when the agent may not open the ticket). | A file bigger than the cap needs osTicket's UI; a payload this size briefly sits in the inbox row until the command finishes (a pending or killed command keeps it). | Streaming uploads only if the caps prove too small |
| **Only files in osTicket's database storage (backend `D`, its default) can be downloaded.** A file kept by a storage plugin (filesystem, S3) is listed but its download answers 501. Files attached to a ticket's *form fields* (file-upload custom fields) and to canned responses / FAQs are not exposed. Downloads are always sent as an attachment, never rendered inline, and the file's stored type is passed through only if it is a well-formed media type. | A helpdesk using a storage plugin cannot download through the API. | A bridge read mode (planned "HTTP fallback read mode"), where osTicket's own backend reads the file |

## Login and abuse protection

| Limit | Impact | Resolved by |
|---|---|---|
| **Accounts with two-factor authentication — or that osTicket requires to enrol — cannot use the API.** They are refused with `two_factor_required`. | Use a non-2FA agent account for API access. | By design until a second-step login endpoint exists |
| **A password change ends older sessions, compared to the second.** A token issued in the same second as the change survives, and the API and database clocks are assumed to agree (they share a host in the compose stack). | Negligible in practice; a skewed clock on a split deployment could end sessions early or late by the skew. | By design |
| **A repeated `Idempotency-Key` is checked against the stored command's type, resource and body, leaving out secret fields** (a password cannot be compared once the bridge has scrubbed it). | Reusing a key for a staff create or update with only a different password is treated as a retry. | By design |
| **The login lockout is in memory and per process.** The default rate limit is per process too unless `RATE_LIMIT_STORAGE_URI` points at Redis. | With N API workers the effective allowance is N times higher, and a restart clears lockouts. | A shared store (Redis) if you run several workers |
| **No refresh tokens.** | Clients log in again every `ACCESS_TOKEN_EXPIRE_MINUTES`. | By design (cost/benefit) |
| **The 2FA and forced-password-change login refusals are verified by hand, not by an automated test.** | No e2e path can put an agent into those states. | — (a PHP test runner would fix it) |

## Events, latency and caching (Phases 3–4)

| Limit | Impact | Resolved by |
|---|---|---|
| **WebSocket delivery is best-effort and not replayed.** Each API process starts at the end of the outbox and pushes what arrives after; an event written while a process was down, or before a client connected, is not delivered, and there are no event ids to resume from. | A client that reconnects must refetch what it cares about. | By design (the REST reads are the source of truth) |
| **Ticket and task events follow the agent's *list* visibility**, and deletions go to administrators only (the row is gone, so no one "can see" it). | An agent who can open a closed ticket only through a referral (page yes, list no) is not told about its changes; an agent is not told when a ticket they could see is deleted. | By design (narrower is safer) |
| **Open connections notice a disabled account or an expired token within `WS_RECHECK_SECONDS` (15 s)**, not instantly. | A disabled agent can keep receiving for up to that long. | Tunable; an event-driven close on `staff.*` events would make it immediate |
| **WebSocket connection attempts are not rate limited** (the HTTP middleware does not cover them); an agent is capped at `WS_MAX_CONNECTIONS_PER_STAFF`. | An unauthenticated client can open connections at will, each costing a token check. | Later (a connection-rate limit or a proxy rule) |
| **Every agent login sends administrators a `staff.updated` event** (osTicket's last-login update fires the model signal). | Noise on the admin stream. | Later (drop signal events that change only `lastlogin`) |
| **The outbox's `status`, `retry_count` and `locked_at` columns are unused.** The API reads the outbox by cursor and never claims or retries a row. | Dead schema in `bridge/schema.php`. | Later (drop them in a schema upgrade) |
| **Part of an agent's access is cached for up to `ACCESS_CACHE_TTL_SECONDS` (5 s) per process.** The staff row (enabled, admin, global permissions, primary role) is read on every request; extra-department roles, role permission maps, teams and visible departments are reused. Bridge changes to staff, departments and teams clear it (on the outbox event in every process, and at once in the process that serves the finished command). | A role's permission map, a team membership or a department tree changed directly in osTicket's UI, or a bridge change served by another process before its event arrives, can take up to the TTL to apply. Set the TTL to 0 for none. The cache is per process and is not shared (no Redis). The WebSocket re-check reads it too. | By design (short TTL); a shared store only if measured to pay off |
| **Each ticket or task event still costs one visibility query per connected agent** (`ticket_is_visible`); the access cache does not help it. | Many connected agents and a busy helpdesk mean many small queries per event. | Later (a set-based check or a visibility cache) |
| **Without PHP's `pcntl` extension the worker exits after each command** and the supervisor restarts it. | Commands still run, but slower and subject to restart backoff; `make doctor` warns. | Install `pcntl` |
| **osTicket's cron fallback runs about once a minute.** | If no worker runs, a command can wait up to ~60 s. | Run the worker |

## Compatibility and deployment

| Limit | Impact | Resolved by |
|---|---|---|
| **The timestamp conversion is proven only against a UTC database.** The API answers every osTicket timestamp as UTC with a `Z`, reading osTicket's naive values in the database's timezone (`DB_TIMEZONE`, else osTicket's `db_timezone`, else the server's; unit-tested with Berlin and New York, but the live stack's database is UTC). An abbreviation such as `CEST` is not guessed: it falls back to UTC and `make doctor` warns. The bridge's own clock checks (`DATE_SUB(NOW(), ...)` against rows the API stamped with UTC) and the outbox purge also assume the database runs in UTC. | On a database in another timezone, set `DB_TIMEZONE` and check `make doctor`; the stale-command check and the purge can be off by the offset. | Running the e2e suite against a non-UTC database |
| **Only osTicket 1.18.1 and MariaDB 10.11 have been tested.** `schema.php` is written for MySQL 5.6+ and the queries for the 1.18 schema, but nothing else has run. | `make doctor` warns on other versions and names any read query that breaks; the bridge handlers may still differ. | Running the e2e suite on each target |
| **Installing the plugin zip through osTicket's admin panel is untested.** Only the CLI installer (used by the Docker image) has been run. | Expect to check the plugin appears, enables and creates its tables. | Trying it on a real instance |
| **The compose stack uses one all-privileges database user** for osTicket, the plugin and the API. | `make doctor` warns; production should give the API the least-privilege grants it prints. | Splitting users in `docker-compose.yml` |
| **The oracle test compares list visibility, page visibility, department and topic names, canned pickers, the default ticket queues, the agent directory and the assign-form agents and teams with osTicket's own PHP, not every read.** `tests/e2e/test_oracle.py` builds a throwaway scenario (sub-departments, a managed department, extra-department access, `assigned_only`, a global-permission agent, referrals, team assignment, merged-child-style threads) and diffs the API against osTicket's own methods. Reads outside that list (user/org directories, KB, thread bodies and attachments, search over users, task lists) rest on the SQL-semantics tests and on osTicket's source as read. | A rule in an unlisted read could differ from osTicket without a test noticing. | Extending `oracle.php` read by read |

## Hardening and deployment security (S6)

| Limit | Impact | Resolved by |
|---|---|---|
| **The dev API container runs as root and the compose stack publishes on all interfaces without TLS.** | Fine on a laptop; on a server put a TLS-terminating proxy in front, bind ports to localhost, and run the container as a non-root user. | Production compose profile |
| **Login timing may reveal whether a username exists** (osTicket's own backend decides; the API only throttles). | An attacker can guess usernames slowly; lockout limits password guessing. | By design (osTicket's behaviour) |
| **Dependencies have not been audited against an advisory database** (no `pip-audit` run in CI). | A vulnerable pinned package would go unnoticed. | Add an audit step to CI |
